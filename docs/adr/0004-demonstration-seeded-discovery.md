# ADR 0004: escalate discovery with demonstration seeding

Status: accepted. Date: 2026-06-11.

## Context

Five 10M-step arms all evaluate at clear_rate 0.00 (ledger-backed): the clip
baseline, reward scaling (E1, a literal no-op), gamma 0.999 (E2), RND (E3,
which also degraded score), higher entropy (E4), and no-sticky training (E5).
E6 (minimal action set) is pending; the in-training clear rate logging shows
zero across roughly 30,000 cumulative episodes.

The mechanism is structural. Reaching the top of the barrels screen requires
a multi-second, zero-reward, high-death-risk action chain (climb four floors
while dodging streamed barrels), while the bottom ramp pays +100 per barrel
jump. Neither stochasticity (E4, E5) nor state novelty (E3) produces a
surviving climb even once, so no value-based method has anything to credit.

## Decision

Two-track escalation:

1. E7 control arm (cheap, immediate): stack all discovery levers (no sticky,
   minimal actions, ent_coef 0.05, scale transform) in one run. Tests lever
   composition while track 2 is built.
2. Demonstration seeding (the main track): script a rule-based climbing
   policy using RAM state via ale-py (OCAtari documents the DonkeyKong RAM
   layout), collect demonstration episodes that clear screen 1, and use them
   to warm-start PPO with behavior cloning before EnvPool fine-tuning.
   This is the kickstarting/DQfD-family approach, justified here because the
   blocker is pure discovery, not credit assignment: one successful
   trajectory distribution in the policy prior changes what PPO can reach.

Demonstrations are generated by our own scripted policy, not human play, so
the method stays fully reproducible from the repo (the script is code, the
demos regenerate deterministically given seeds).

## Consequences

- The paper's narrative sharpens: a systematic ladder of standard fixes,
  each measured at zero, then a discovery transplant that (if it works)
  isolates exactly what DonkeyKong demands.
- BC warm-start adds code: demonstration collection module, a BC pretraining
  step, and a config switch. Each is a typed config field and ablatable
  (e.g. number of demo episodes, BC epochs).
- Risk: the scripted policy may be hard to make reliable under sticky
  actions. Mitigation: collect demos without sticky actions; BC tolerates
  distribution shift better than the zero-discovery alternative.
